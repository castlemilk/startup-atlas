# Query console (DuckDB-WASM in the browser)

The Query page (`query.html`) lets anyone run analytical SQL against the
published Atlas catalogue in their own browser. Queries execute locally —
no request leaves the device except fetching the published dataset files.

## Data flow

```
data/*.json (reviewed, published)
  → scripts/build-query-parquet.py   (build time, needs pyarrow)
  → dist/data/query/*.parquet + manifest.json
  → query.html fetches manifest.json
  → DuckDB-WASM (vendored, in a Web Worker) creates one view per table
  → user SQL runs read-only against those views
```

### Tables

Generated by `scripts/build-query-parquet.py` from the reviewed JSON files
only (`catalogue.json`, `partners-reviewed.json`, `partner-profiles.json`,
`startup-research.json`). An unreviewed file under `data/` cannot leak into
the query dataset: the generator has an explicit input allowlist, mirroring
`scripts/build-graph-db.py`.

| Table | Source | Contents |
|---|---|---|
| `opportunities` | `catalogue.json` | Every published opportunity (id, org, kind, access, scope, value, status, …) |
| `partners` | `partners-reviewed.json` + `partner-profiles.json` | Reviewed partners, with profile type/geography where one exists |
| `partner_leads` | `catalogue.json` | Every partner lead name, with a `reviewed` flag |
| `startups` | `startup-research.json` | Startup name, website, description, `founded_year`, `reviewed_at` |
| `funding_rounds` | `startup-research.json` | One row per round (amount, currency, stage, announced_on, …) |
| `articles` | `startup-research.json` | One row per article |
| `profile_facts` | `startup-research.json` | One row per profile fact |
| `founders` | `startup-research.json` | One row per founder |
| `socials` | `startup-research.json` | One row per recorded social link |

Amounts are stored as recorded (`amount` + `currency`, or `amount_text`
when the source never stated a currency). Nothing is converted here; the
currency rules in `docs/CURRENCY.md` apply at collection time.

`dist/data/query/manifest.json` records the generator version, the UTC
generation time, the source revision, and each table's file, row count and
columns. The page renders the manifest as its schema sidebar and provenance
line.

## Runtime

- **Engine:** `@duckdb/duckdb-wasm` 1.32.0 (pinned exact), vendored into
  `dist/vendor/duckdb/` by `scripts/build.mjs`. No CDN: the site is
  self-hosted. Install with `npm install --save-exact @duckdb/duckdb-wasm@1.32.0`;
  the build fails with a clear message if the package is missing.
- **Worker:** DuckDB instantiates its own Web Worker from the vendored
  worker script, so queries never block the page. `selectBundle` picks the
  fastest bundle the browser supports (MVP or EH). The threaded (`coi`)
  bundle is not offered: it needs cross-origin isolation headers that
  GitHub Pages does not send.
- **Lazy loading:** the homepage and other pages load nothing extra. The
  query page fetches the (small) manifest on load, then loads the DuckDB
  engine and the Parquet files on first use. The engine is ~10 MB of WASM;
  the dataset is ~100 KB of Parquet at current size.
- **Read-only guard:** `web/query.js` accepts only a single `SELECT` (or
  `WITH … SELECT`) statement and rejects `ATTACH`, `COPY`, `INSERT`,
  `UPDATE`, `DELETE`, `DROP`, `CREATE`, `PRAGMA` and friends before the
  SQL reaches DuckDB. This is a UX guard, not a security boundary — the
  browser database holds only public data and is discarded on navigation.
- **Sharing:** `query.html?sql=SELECT …` prefills the editor and runs the
  query once the engine is ready.

## Why DuckDB-WASM instead of the existing SQLite/Fuse approach

The site already has two query paths, and the console does not replace
either:

- **SQLite + FTS4** (`dist/data/atlas.sqlite`, `web/graph-sql.js`) is the
  graph explorer's store: entity lookup, full-text search and relationship
  traversal over the graph. It is row-oriented and queried through sql.js.
- **Fuse** powers the directory's fuzzy text search over the published
  catalogue + reviewed partners.
- **DuckDB + Parquet** is the analytical path: columnar storage, SQL
  aggregations (`GROUP BY`, `SUM`, window functions), and joins across
  tables — the questions the other two cannot express ("total AUD raised
  per startup", "opportunities by kind", "leads not yet reviewed").
  Parquet also scales: if the published dataset grows (the partners crawl
  alone has ~4,700 candidates), columnar files and predicate pushdown keep
  queries fast without shipping the whole dataset into memory.

## Build wiring

- `npm run build` runs `python3 scripts/build-query-parquet.py` after
  `build-graph-db.py`. The script needs `pyarrow`; the Pages workflow
  installs it (`pip install pyarrow`) before the main-branch build. Without
  pyarrow the script exits 2 with an explicit message instead of publishing
  a stale or missing dataset.
- `scripts/build.mjs` copies `web/query.html`, `web/query.js`, `web/query.css`
  into `dist/`, versions the query assets with the UI fingerprint, and
  vendors the DuckDB files into `dist/vendor/duckdb/`.
- `web/atlas-ui.js` adds Query to the view navigation and to the
  `safeAtlasReturn` route allowlist.

## Tests

- `tests/test_query_parquet.py` — generates the dataset into a temp dir and
  checks every table's row count against its source JSON, the manifest's
  contents and revision, and the fail-loud behaviour without pyarrow. It
  skips cleanly where pyarrow is absent. Wired into the `data` lane in
  `scripts/check_ci_paths.py` and the Pages workflow's data-validation step.
- The example queries in `web/query.js` were verified against the generated
  Parquet with the Python DuckDB client during development; the browser
  runtime wiring (worker creation, bundle selection) follows the documented
  DuckDB-WASM instantiation pattern and still needs a live browser check.

## Still missing

- **Live browser verification** of the query page (engine load, worker,
  a query run, CSV download). The VM has no browser; verify on the deployed
  Pages site after merge.
- **Full-text search inside SQL**: DuckDB has no FTS over these tables yet;
  use the directory search or the SQLite snapshot for text search.
- **Larger datasets**: the generator covers the reviewed catalogue only.
  Unreviewed crawl candidates (partners, profiles, logos) are not included
  by design; adding them would need the same review gate the rest of the
  site uses.
- **Saved/shared queries beyond `?sql=`**: no history or saved-query store
  yet.
