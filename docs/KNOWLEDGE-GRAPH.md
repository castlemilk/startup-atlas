# Startup Atlas knowledge graph

The graph has separate startup, person, partner, provider and programme entities; source-attributed edges; funding events; and news links. `data/startup-research.json` is the reviewed startup overlay. Existing portfolio and provider records are incorporated without claiming that a portfolio listing is a funding round or that a screenshot proves an entitlement. IDs are `kind:slug` (programmes use their catalogue ID); identifier collisions fail the build instead of silently merging entities. People listed on a partner profile have firm-scoped IDs until their identities are explicitly reconciled, so a matching name alone does not merge them with a founder.

## Storage and search

The public GitHub repository is the durable source of reviewed records. `npm run build` regenerates the graph and compiles it to `dist/data/atlas.sqlite` using Python's SQLite and FTS4. The explorer downloads this immutable snapshot and searches it locally with the self-hosted SQLite WebAssembly runtime; it does not send search queries to a paid service. Indexed text includes startup, partner, provider, person and programme names, sourced connections, funding stages and article titles. If WebAssembly or the database cannot load, the matching JSON snapshot supports navigation and search with a visible fallback notice.

The visual explorer uses the [Loom renderer](https://castlemilk.github.io/loom/) with a compatibility SVG map for browsers without WebGL2. Activating a node follows all matching connections at the selected depth. Browser history restores earlier neighbourhoods, and the equivalent list presents directed relationships and their source links. Partner company and team links open dedicated profiles, including a founder’s other researched startups. Programme profiles display the reviewed catalogue terms with the recorded check date and supporting sources. **Find startups & people** passes the main directory query to graph search.

The database includes graph entities, sourced edges, rounds and articles, plus all current public structured data files in `source_documents` (with SHA-256 hashes). It also exposes the full opportunity records and their addition provenance, partner leads/reviewed records/profiles, locations, reviewed logo mappings and provider-relationship records in separate tables. The explicit input allowlist in `scripts/build-graph-db.py` prevents unrelated future files from being published accidentally; add a new public dataset deliberately and extend the parity tests. Logo/image bytes remain separate assets or external references. Screenshot-only relationships keep their unverified labels and null source. The main directory and partner profile pages still read their existing JSON and JavaScript files; migrating those readers to the database is separate work.

Each merge to `main` rebuilds the index and deploys it to GitHub Pages. The Pages workflow also rebuilds daily at 03:17 UTC. Scheduled runs can be delayed by GitHub and are automatically disabled after 60 days without repository activity. The publication records its exact source commit as `source_revision`. Graph read tools in the hosted MCP use the published graph from the same build and report its revision, the current `main` revision, and whether publication is pending. A draft PR is never treated as published data.

The publication check compares the catalogue and deployed public JSON against the corresponding SQLite records, in addition to graph counts and the source revision. For the remaining identity, provenance, crawler, profile and graph-explorer work, see the [knowledge graph roadmap](KNOWLEDGE-GRAPH-ROADMAP.md).

The `atlas.sqlite` file is a downloadable read model, not a shared, writable browser database. The entire file is loaded into each browser's memory, which is appropriate for the current small dataset; revisit sharding or a server-side index as it grows. There is no R2 bucket, Supabase project or new paid hosting service in this path. Standard GitHub-hosted runners for public repositories and public GitHub Pages are free within GitHub's published limits; watch account storage and service limits rather than assuming unlimited usage. Existing private MCP hosting and OAuth storage are unchanged.

## Startup updates via MCP

For existing startup records, prefer the canonical-ID
[record editing contract](MCP-RECORD-EDITS.md): authoritative overlay reads,
record digests, complete merged validation, typed startup/founder social
references, source-inheritance guards and read-only proposal recovery. This is
separate from the published graph read. Discover the deployed tool catalogue
before relying on the new source implementation; the legacy addition workflow
below remains available with its existing semantics.

The hosted MCP source defines `atlas_validate_startup` and `atlas_propose_startup`. Validate first to obtain the current `main` revision and inspect the merged preview. Then propose using that exact revision. The proposal creates a draft PR changing only `data/startup-research.json`; it does not merge or publish. Updates preserve omitted founders, rounds, articles and relationships; matching items are merged by identifier. Omitted fields on an existing funding event preserve previous values; omission or `amount_text` is not a deletion operation. Replacing a funding source requires explicitly resubmitting every existing claim against that source, otherwise validation and proposal fail with `SOURCE_INHERITANCE`. An unsupported numeric claim that must be removed needs a separately reviewed correction, not an omission-only upsert. A new startup needs an official website, description, source and review date. Each funding event and relationship needs its own source; amounts and valuations require explicit currencies. Logo and founder-photo URLs require attribution. Validate checks format and collisions, not whether claims are true.

If a proposal write is uncertain, inspect its deterministic branch and PR before retrying. Its identity is independent of the main revision and object key order; equivalent normalized startup names share one identity. Unrelated main changes cannot turn the same intent into a second draft. The source implementation returns an existing receipt only after verifying the exact one-file update, history and PR head; it never completes a partial branch without a confirmed PR. Unverified state requires manual inspection. Never guess whether an uncertain GitHub write succeeded. Merging the reviewed PR initiates a Pages rebuild; check the deployment and the MCP's published revision before relying on the result. The private MCP Site is a separate deployment from GitHub Pages: repository changes alone do not activate new tools. Preserve its existing OAuth, identity, access and D1 bindings when publishing.

The existing Buf/Connect-Go API and optional Supabase adapter remain in the repository for future use, but neither is needed by the free static deployment. Do not enable that adapter or move the source of truth without an explicit migration and parity checks.

## News discovery

Run `npm run crawl -- news --follow 2` against `data/startup-news-sources.json`, or dispatch the existing Partner research crawl workflow. Only curated HTTPS source hosts are fetched; host restrictions, rate limits, public-address checks and response limits are inherited from the collector. `research/crawl/latest-news.json` contains unreviewed article URLs, amount mentions and source evidence. Verify the primary announcement, company, date, currency, round and any investor claims before adding them to the graph. An amount in a page navigation or customer story is not automatically a funding event. The collector does not request robots.txt or bypass access controls.


### Reviewed company details

Startup research records can include `profile_facts`: a list of stable keys, display labels, values, HTTPS evidence URLs and review dates. Capture historical dates or locations with their as-of context, and keep unknown fields absent. An omitted `founded_year` remains absent in the generated graph and SQLite entity JSON, whether or not the company was already listed in a partner portfolio; it is never synthesized as year zero. Founders and funding remain separate, source-backed graph records. The profile renders founder relationships prominently and displays each company fact with its own source; these facts flow into both the SQLite snapshot and JSON fallback. Hosted MCP startup validation accepts and merges facts by key, but its deployment must be verified separately from the static site.

## Company treemaps

`treemap.html` reads the same immutable graph through `openGraph`, with SQLite and JSON fallback. Three presentations share the same records and filters: a proportional treemap, ranked company cards, and a keyboard-accessible list. The cards emphasize the first three entries, then use a compact responsive grid with logos or initials, figures, announcement dates and recorded founding years. Card area is editorial, not proportional to value; the treemap remains the area comparison. Financial views sort by recorded amount, while equal-weight company cards use alphabetical order without implying a financial rank.

All presentations include profile/source links, name/description search and founding-decade filters. Treemap and card views let a founding-decade group drill down to its companies. Filter, presentation and selected-company state are shareable in the URL and restore on Back/Forward. `?view=cards` opens cards and `company=<entity ID>` restores the evidence panel when that company is present in the filtered view. **Share view** copies this URL; if clipboard access is unavailable, the button directs the user to copy the address bar. Missing founding years (including placeholder zero) remain “Not recorded”. No sector, geography, revenue or headcount is inferred.

Valuation uses each company's latest **dated, positive numeric valuation in the selected currency** with an HTTPS source. Funding announcement uses the latest **dated, positive numeric event amount in that currency**. The values are historical observations from different dates, not current valuations or cumulative funding. No FX conversions or overlapping round sums are performed. Text-only values, missing currencies/dates, zero and invalid values are excluded and counted visibly, not converted into zero. A newer unplotted event is flagged in the selected company detail; all events remain available on its profile. Same-date ties use stable event ID ordering. Company count includes all matching companies with equal weight. Colors indicate recorded founding decades, not performance or investment advice.

The browser supports resize, reduced motion, source notes, failed-logo initials, empty filters and unavailable snapshots. A card also flags when a newer announcement is not plotted. Unit tests cover metric selection, missing values, dates, currencies, deterministic grouping and proportional layout. `node scripts/test-treemap-browser.mjs` exercises SQLite, JSON fallback, load failure, filtering, card order and cohort drill-down, shared selection and history, keyboard/profile navigation and desktop/mobile layouts against the production build.
