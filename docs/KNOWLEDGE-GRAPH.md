# Startup Atlas knowledge graph

The graph has separate startup, person, partner and provider entities; source-attributed edges; funding events; and news links. `data/startup-research.json` is the reviewed startup overlay. Existing portfolio and provider records are incorporated without claiming that a portfolio listing is a funding round or that a screenshot proves an entitlement. IDs are `kind:slug`; identifier collisions fail the build instead of silently merging entities.

## Storage and search

The public GitHub repository is the durable source of reviewed records. `npm run build` regenerates the graph and compiles it to `dist/data/atlas.sqlite` using Python's SQLite and FTS4. The explorer downloads this immutable snapshot and searches it locally with the self-hosted SQLite WebAssembly runtime; it does not send search queries to a paid service. Indexed text includes sourced connections, funding stages and article titles. If WebAssembly or the database cannot load, a basic JSON search remains available and the UI indicates reduced search coverage.

The database includes graph entities, sourced edges, rounds and articles, plus all current public structured data files in `source_documents` (with SHA-256 hashes). It also exposes the full opportunity records and their addition provenance, partner leads/reviewed records/profiles, locations, reviewed logo mappings and provider-relationship records in separate tables. The explicit input allowlist in `scripts/build-graph-db.py` prevents unrelated future files from being published accidentally; add a new public dataset deliberately and extend the parity tests. Logo/image bytes remain separate assets or external references. Screenshot-only relationships keep their unverified labels and null source. The main directory and partner profile pages still read their existing JSON and JavaScript files; migrating those readers to the database is separate work.

Each merge to `main` rebuilds the index and deploys it to GitHub Pages. The Pages workflow also rebuilds daily at 03:17 UTC. Scheduled runs can be delayed by GitHub and are automatically disabled after 60 days without repository activity. The publication records its exact source commit as `source_revision`. Graph read tools in the hosted MCP use the published graph from the same build and report its revision, the current `main` revision, and whether publication is pending. A draft PR is never treated as published data.

The publication check compares the catalogue and deployed public JSON against the corresponding SQLite records, in addition to graph counts and the source revision. For the remaining identity, provenance, crawler, profile and graph-explorer work, see the [knowledge graph roadmap](KNOWLEDGE-GRAPH-ROADMAP.md).

The `atlas.sqlite` file is a downloadable read model, not a shared, writable browser database. The entire file is loaded into each browser's memory, which is appropriate for the current small dataset; revisit sharding or a server-side index as it grows. There is no R2 bucket, Supabase project or new paid hosting service in this path. Standard GitHub-hosted runners for public repositories and public GitHub Pages are free within GitHub's published limits; watch account storage and service limits rather than assuming unlimited usage. Existing private MCP hosting and OAuth storage are unchanged.

## Startup updates via MCP

The hosted MCP source defines `atlas_validate_startup` and `atlas_propose_startup`. Validate first to obtain the current `main` revision and inspect the merged preview. Then propose using that exact revision. The proposal creates a draft PR changing only `data/startup-research.json`; it does not merge or publish. Updates preserve omitted founders, rounds, articles and relationships; matching items are merged by identifier. A new startup needs an official website, description, source and review date. Each funding event and relationship needs its own source; amounts and valuations require explicit currencies. Logo and founder-photo URLs require attribution. Validate checks format and collisions, not whether claims are true.

If a proposal write is uncertain, inspect its deterministic branch and PR before retrying. Never guess whether an uncertain GitHub write succeeded. Merging the reviewed PR initiates a Pages rebuild; check the deployment and the MCP's published revision before relying on the result. The private MCP Site is a separate deployment from GitHub Pages: repository changes alone do not activate new tools. Preserve its existing OAuth, identity, access and D1 bindings when publishing.

The existing Buf/Connect-Go API and optional Supabase adapter remain in the repository for future use, but neither is needed by the free static deployment. Do not enable that adapter or move the source of truth without an explicit migration and parity checks.

## News discovery

Run `npm run crawl -- news --follow 2` against `data/startup-news-sources.json`, or dispatch the existing Partner research crawl workflow. Only curated HTTPS source hosts are fetched; host restrictions, rate limits, public-address checks and response limits are inherited from the collector. `research/crawl/latest-news.json` contains unreviewed article URLs, amount mentions and source evidence. Verify the primary announcement, company, date, currency, round and any investor claims before adding them to the graph. An amount in a page navigation or customer story is not automatically a funding event. The collector does not request robots.txt or bypass access controls.
