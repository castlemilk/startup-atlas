# Image format fixtures and conversion review contract

This packet contains synthetic acceptance fixtures and a review contract. It
does not contain a converter, extend the admitted image formats, enable image
upload, attach a record or authorize publication. The existing
[`scripts/atlas_assets.py`](../../scripts/atlas_assets.py) helper remains unchanged.
JPEG, all SVG and PNG files with ancillary chunks continue to fail its strict
PNG profile. A rejected image remains a private candidate or a useful source
link; rejection never triggers automatic conversion.

## Representative synthetic files

[`image_fixtures.py`](image_fixtures.py) creates original geometric raster bytes.
The logo-shaped fixtures do not identify a brand; the portrait-shaped fixture is
an abstract head-and-shoulders silhouette, not a photograph or identified person.
No real company image, headshot or downloaded source asset was converted.

| Fixture | Actual format and content | Current strict helper result |
| --- | --- | --- |
| `logo-rgb` | 48 × 32, 8-bit RGB PNG, geometric bars | Accepted format |
| `logo-rgba` | 48 × 32, 8-bit RGBA PNG, geometric ring with alpha values 0, 128 and 255 | Accepted format |
| `portrait-rgb` | 48 × 64, 8-bit RGB PNG, abstract silhouette | Accepted format |
| `complete-jpeg` | Complete 16 × 16 RGB JPEG with gradient pixels, quantization/Huffman/frame/scan data and end marker | Rejected |
| `benign-svg` and `active-svg` | A plain rectangle SVG and an explicitly active-content SVG fixture | Both rejected |
| `png-tEXt` | Accepted RGB fixture plus a valid-CRC text metadata chunk | Rejected without stripping |
| `png-iCCP` | Accepted RGB fixture plus a valid-CRC compressed, generated sRGB profile | Rejected without stripping |
| `png-eXIf` | Accepted RGB fixture plus a valid-CRC TIFF orientation=6 entry | Rejected without applying orientation |
| `png-gAMA` | Accepted RGB fixture plus a valid-CRC gamma value of 45455 | Rejected without reinterpretation |

All accepted PNGs contain exactly IHDR, IDAT and IEND, are non-interlaced, and
use filter 0. The procedural encoder uses explicit stored DEFLATE blocks so
their bytes do not depend on compressor-version choices. The
[`image-cases.json`](fixtures/image-cases.json) registry records every exact
fixture digest, byte count, declared MIME and expected result. A test compares
that registry against the generated bytes and invokes the existing strict helper.
Format acceptance does not approve a subject, provenance, rights or attachment.

The JPEG was created once from specified synthetic RGB pixels with the already
available Pillow **13.0.0**, JPEG codec **6.2**, libjpeg-turbo **3.2.0**. The exact
parameters are `quality=85`, `subsampling=0`, `optimize=False`,
`progressive=False`, with RGB 16 × 16 input. An executed `Image.open(...).load()`
check decoded RGB 16 × 16. The complete 770-byte output is frozen as base64 with
SHA-256 `4aa80df28941dcfae2a76f4a5d46d3a4b9f5644f1ec84356f7d2d2f0492dac20`.
CI checks the frozen digest and complete marker structure; it does not claim to
run a JPEG decoder. Pillow is not a new project or runtime dependency.

The iCCP profile was generated once by Pillow ImageCms 13.0.0 / LittleCMS 2.19
using `createProfile('sRGB')`. Its complete frozen bytes and hash are recorded
in the helper. The timestamp-bearing profile header is not regenerated during
tests. This fixture tests rejection of meaningful ancillary data; it does not
establish a general color-conversion implementation.

## Preserve the original and distinguish every derivative

Before considering any transformation, retain the exact acquired original
bytes in the private evidence store, their SHA-256, byte count, supplied and
observed MIME when available, acquisition URL/time, subject evidence and the
original provenance/rights review. A URL is not a substitute for those bytes.
Do not overwrite the original, replace its digest with the output digest, or
describe a missing HTTP MIME as observed. Original private provenance stays
available even when a proposed public disclosure omits sensitive material.

The merged `StageStore` accepts only the strict PNG subset. It cannot hold an
unsupported original JPEG or ancillary-chunk PNG as a validated image asset.
Exact original custody is a separate private opaque-capture prerequisite under
the existing staging and retention policy, with original-byte readback, digest
and provenance verified before any proposed conversion. The collector's opaque
`.bin` candidates illustrate that distinction; their presence alone does not
clear identity or rights. This packet adds no original-store service or recovery
mechanism. An original rejected as unsupported is not thereby corrupt, and must
not be deleted or silently replaced by a derivative.

An actual conversion produces a separately identified derivative: new exact
bytes, content SHA-256, asset ID, measured MIME/size/dimensions, and a distinct
review manifest revision covering the derivative and its allowed use. The
derivative manifest must refer to the original identity and private lineage
record through the reviewed access boundary. It cannot reuse the original
review digest for different bytes or silently inherit its approvals. An
operation that leaves bytes identical is recorded as a verified no-op; it does
not manufacture a distinct content digest or claim a completed conversion.

Every conversion receipt must bind the exact tool, version, build/codec version
where it affects output, complete parameters, original input digest, resulting
output digest and execution/check time. Retain both requested parameters and
effective settings, including defaults. A tool name such as “Pillow”, “browser”
or “ImageMagick” without an exact version and settings is insufficient. The
eventual converter and its decoder/resource sandbox need separate review; this
packet chooses neither a converter nor a service.

## Transformation decisions must be explicit

Each row needs a recorded operation or an explicit no-op/preserve decision,
plus the relevant permission evidence. A preset named “web safe” does not
replace these decisions.

| Area | Required decision and evidence |
| --- | --- |
| Crop | Exact input coordinate system, bounds, alignment and output extent; or preserve the whole frame. A portrait crop needs renewed subject/content review. |
| Resize | Exact output dimensions, aspect-ratio behavior, upscaling decision and resampling algorithm; or preserve pixel dimensions. Record any padding or added canvas. |
| Alpha | Preserve, introduce or flatten transparency; specify matte/background color, premultiplication behavior and output channel model. Partial alpha is not interchangeable with opaque pixels. |
| Color and channel conversion | Input and output color interpretation, RGB/RGBA channel choice, bit depth, rendering intent, transfer/gamma treatment and gamut/clipping decision; or preserve the measured model. “Looks correct” is not a color specification. |
| EXIF orientation | Record the original orientation value, whether pixels are physically rotated/flipped, output dimensions and the disposition of the orientation tag. Explicitly record no tag/no-op; never double-apply orientation. |
| ICC profile and gamma | Identify input profile/gamma bytes by digest, conversion/profile assignment and output interpretation, plus the planned retention or removal of each tag. Removing a profile without a corresponding reviewed color decision can change rendering. |
| Metadata | Inventory text, copyright, attribution, EXIF and other ancillary chunks; record each retained, transformed or removed item and why. The current strict PNG subset admits no ancillary chunks, so preparing an output for it would require an explicit metadata-removal decision, not silent stripping. |
| Encoding | Exact output MIME, compression/filter/interlace settings and deterministic-output expectations. Re-encoding changes bytes even where decoded pixels appear unchanged. |
| Other edits | Explicitly enumerate compositing, sharpening, denoising, retouching, background removal, generated filling or similar work. An omitted operation is not approved. |

An asset being downloadable, a source repository having a code licence, a
converter being able to decode it, or the original being approved for display
does not establish permission to transform it. The review needs the applicable
licence/permission evidence, scope of allowed modifications, attribution terms,
subject/content decision, reviewer and time. Unknown or rejected transformation
rights stop the operation. A decoder or validation success cannot change that
decision. Public repository storage and website display remain separate,
explicit use decisions after the derivative itself is reviewed.

When an approved transformation removes embedded attribution or copyright
metadata, retain any required credit and terms out of band in the reviewed
provenance and appropriate public attribution. The strict output format is not
permission to drop those obligations. Keep private correspondence and unrelated
sensitive metadata private; choose the public disclosure separately.

## Proposed lineage evidence remains private

The following is a **proposal shape for review**, not a production schema or an
accepted MCP argument. It refers only to the synthetic JPEG fixture above.
`null` means that a derivative or tool choice does not yet exist; it is never a
successful conversion receipt.

{
  "status": "proposal_only",
  "scope": "synthetic_fixture",
  "original": {
    "sha256": "4aa80df28941dcfae2a76f4a5d46d3a4b9f5644f1ec84356f7d2d2f0492dac20",
    "mime": "image/jpeg",
    "bytes": 770,
    "private_provenance_revision": null
  },
  "derivative": null,
  "tool": null,
  "effective_parameters": null,

Before execution, pending decisions must become explicit approved operations or
no-ops. After execution, a complete receipt must add actual derivative identity,
before/after MIME and size, measured dimensions, original and derivative review
revisions, exact tool/parameters and retained permission evidence. Those private
records can contain reviewer context, permission correspondence and acquisition
details that must not be copied to a public manifest automatically.

A public disclosure is a separately reviewed projection with its own digest.
It may contain only the approved source/attribution, content identity and
appropriate transformation disclosure. Redacted bytes cannot retain the full
private manifest's digest. Neither a private lineage link nor a public-safe
projection proves publication authority; the production review mechanism is
still unresolved in this source-only packet.

## Validate, attach and release through the existing owners

The derivative must pass the unchanged strict byte validator from its actual
output bytes, including MIME/signature, full PNG structure/CRC/zlib/filters,
dimension/pixel/byte limits and all prohibited-content rules. A conversion
receipt does not exempt it. Then validate complete derivative provenance, retain
the deterministic preflight references, and stage/read back it privately.
The separate [transport contract](transport.py) must measure the complete
eventual request body: a locally accepted image can still exceed the hosted
128 KiB limit after base64 and metadata. No format rejection authorizes chunking,
fetch-by-URL, a new storage service or a larger ingress limit.

The [target/recovery contract](RECOVERY.md#target-and-revision-checks-remain-mandatory)
and the record owner's [strict record edits](../../docs/MCP-RECORD-EDITS.md)
continue to control attachment. Resolve the derivative asset and manifest at
the exact repository commit, preserve the exact subject and role, and use a
fresh expected whole-record revision and strict preview. A founder portrait
still requires the reviewed person-to-founder mapping and exact nested target;
conversion does not resolve an ambiguous identity. Keep original asset identity,
derivative identity, private review revision, public projection revision,
repository commit and record revision distinct.

The public Git repository is an exposure boundary before a draft PR or Pages
release. No original or derivative bytes, private lineage or correspondence may
be uploaded merely to test the converter. An authorized proposal must use the
agreed exact file set and uncertainty recovery path; a draft PR is not a release.
After an authorized release, retrieve the actual image, public manifest and
complete authoritative record, verify the exact digests/MIME/size/dimensions and
source/release revisions, and report any lag or mismatch. Verify private MCP
deployment separately. Conversion, hosted upload, attachment, merge and release
remain held until their own concrete adapters and decisions are reviewed.
