# Hosted OAuth MCP

This is the remote counterpart to `backend/mcp/`, built as a Cloudflare Worker for an **owner-private ChatGPT Site**. The browser directory stays on GitHub Pages. The repository remains the source of truth; D1 stores encrypted OAuth connections, short-lived login state and optional encrypted user-owned GitHub client configuration, not a second catalogue.

## Two separate OAuth connections

1. **MCP client → private Site:** ChatGPT Sites owns MCP OAuth, client connection, access control and trusted identity headers. Publish with the `mcp` capability and connect the private plugin generated by Sites. Do not add a separate MCP token, bypass token, custom authorization server or unauthenticated HTTP bridge.
2. **Private Site → GitHub:** A private GitHub App uses authorization-code OAuth with PKCE `S256`, single-use state and a secure browser-binding cookie. The signed-in Site user explicitly presses **Connect GitHub** and accepts GitHub's authorization screen. No personal access token is supported.

The Worker must only be reachable through Sites dispatch. `oai-authenticated-user-id` is trusted because that boundary authenticates it; these headers alone are not secure on a public `workers.dev` endpoint. Preserve owner-private Site access. Do not publish the raw Worker directly.

## GitHub App registration and consent

No registration, credentials, permissions or live OAuth grants are included in this source. Registration and secret creation/storage require explicit approval at setup time.

- Provider: GitHub.com, using a **GitHub App** (not a classic OAuth App).
- App visibility: private, owned by `castlemilk`.
- Installation: **Only select repositories → startup-atlas**. The server verifies repository ID `1453828311` and rejects an installation that exposes additional repositories.
- Repository permissions: **Contents: read and write**, **Pull requests: read and write**, and GitHub's automatic **Metadata: read**. No Workflows, Actions, Administration, organization or account permissions.
- Authorization request scope: **`offline_access` only**. This requests expiring user access tokens and refresh tokens. Repository permissions come from the GitHub App registration and installation, not broad `repo` or `public_repo` OAuth scopes.
- Authorization endpoint: `https://github.com/login/oauth/authorize`.
- Token endpoint: `https://github.com/login/oauth/access_token`.
- Callback path: **`/auth/github/callback`**. The full callback must be the verified deployed Site origin followed by that exact path, with no query parameters. `PUBLIC_ORIGIN` is a required deployment setting; no unverified hostname is hardcoded here.
- Homepage: the same verified Site origin.
- Use the web authorization flow with expiring user tokens. Device flow and GitHub App private keys are not needed. A client secret is required for the authorization-code exchange.

The token exchange also requests restriction to repository ID `1453828311`, then verifies the authenticated GitHub account, app installation and selected repository. Credential and grant setup must use the GitHub consent/settings pages and secure server-secret entry. Never paste credentials into chat, source control, a client configuration file or browser storage.

GitHub's Contents permission applies to the selected repository as a whole. Application code only creates two data-file changes on a new branch; this code restriction is not a narrower provider-issued credential permission. If a server credential is exposed, the repository could be modified within the granted permissions.

Sources: [GitHub App user authorization](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app) and [GitHub App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).

## Runtime configuration

Non-secret settings:

- `PUBLIC_ORIGIN`: exact verified HTTPS Site origin, without a trailing slash.
- `GITHUB_CLIENT_ID`: registered GitHub App client ID.
- `DB`: private D1 binding with every SQL migration in `backend/hosted/migrations/` applied in filename order through the supported hosting migration workflow. The second migration adds encrypted, user-owned client configuration. Never rewrite an applied migration.

Server secrets, provisioned only with explicit approval:

- `GITHUB_CLIENT_SECRET`: the GitHub App OAuth client secret. When present, this server secret takes precedence over user-owned D1 configuration and disables the setup form.
- `OAUTH_ENCRYPTION_KEY`: a 32-byte AES-GCM key, base64/base64url encoded, used to encrypt connection tokens, login state and optional client configuration. Client configuration authenticates the Site user ID, exact Site origin, GitHub client ID and a distinct purpose/version as AES-GCM context.

With the origin, client ID, encryption key and D1 binding configured, the Site can be privately published and its MCP plugin installed before a client secret is entered. Authenticated MCP discovery and the read-only `atlas_get_connection` readiness tool remain available; GitHub authorization and every repository tool fail closed with `SETUP_REQUIRED` until the caller has a configured secret.

### User-controlled private setup

If the approved existing client secret cannot be transferred through supported secret-to-secret tooling, the owner may enter it directly at `/setup` while signed into the owner-private Site. **The user pastes the existing secret themselves; agents must not read it from a browser or ask for it in chat.** This form does not create a credential, broaden access, or start GitHub consent.

The password field starts blank, uses `autocomplete="new-password"` and submits only by an explicit same-origin POST. The server accepts exactly the action and client-secret fields, rejects duplicates/query parameters, and bounds streamed bodies to 4 KiB and five seconds. It saves AES-GCM ciphertext in a per-user D1 record and redirects to a credential-free success page. Responses do not echo the value; no client scripts, analytics, credential logs or browser storage are used. Existing credentials are never replaced, including during concurrent submissions. There is no MCP tool or API for returning the saved secret and no reset/rotation flow in this feature. An incorrect first entry requires separately authorized administrator recovery; do not generate another credential just to test setup.

Keep the Site owner-private and reachable only through Sites dispatch. Do not widen its audience or publish the raw Worker. A server-provisioned `GITHUB_CLIENT_SECRET` remains supported and takes precedence without deleting any existing user configuration.

OAuth tokens and client secrets never appear in tool responses, browser HTML, logs or local source. Access tokens are renewed only when a connected user calls a repository tool. Refresh uses a database lease and version checks; an uncertain token exchange is not automatically replayed. **Disconnect GitHub** removes the stored connection and attempts to revoke its specific access token, reporting if remote revocation cannot be confirmed. It never revokes the whole grant, which could invalidate a newer connection. The GitHub App authorization/installation remains until removed in GitHub Settings → Applications.

## Repository write behavior

- Search and get opportunities and partner leads read the latest repository commit. Hosted partner search and lookup return existing leads and reviewed metadata, with a common revision, but do not yet write partner records or logos.
- Opportunity validation reads the latest repository commit.
- Add validates evidence, duplicates and the expected main revision.
- It creates a deterministic entry branch and one draft pull request containing only `data/opportunities-added.json` and `data/catalogue.json`.
- It never updates main, changes code/workflows, overwrites an entry, merges or deploys.
- Identical retries inspect the existing branch and PR. A lost write response is reported as uncertain, not replayed blindly.
- A draft PR is a proposed entry, not a deployed change. The existing CI/review/Pages workflow still controls publication.

## Local verification

Use Node.js 22.13+ (tests use the built-in SQLite module to exercise real SQL against an in-memory database).

```sh
npm ci --prefix backend/hosted --ignore-scripts
npm --prefix backend/hosted test
npm --prefix backend/hosted run build
```

The bundle is `backend/hosted/dist/server/index.js`. Tests cover private setup identity/CSRF checks, bounded/deadlined form parsing, ordered SQL migrations, write-once races, per-user encrypted configuration, secret precedence/non-reflection, unconfigured discovery/readiness, OAuth state/PKCE/cookie binding, wrong-account and scope rejection, encrypted storage, refresh races, revocation, authenticated MCP dispatch, data-only GitHub PR writes and lost-response recovery. They use synthetic credentials and mocked GitHub responses; they do not prove live consent or deployed operation.

## Publication checklist

1. Obtain approval for the private Site, private GitHub App registration, selected-repository grants and secure secret creation/storage. Stop if a new charge is presented.
2. Register the owner-private Site once through Sites and persist its returned project ID in its hosting manifest. Use the returned actual origin for `PUBLIC_ORIGIN` and the GitHub App callback.
3. Package this Worker through the supported Sites source workflow with `mcp` capability and the `DB` binding. Apply the included bounded schema migration through that workflow. Do not change the GitHub Pages site's hosting or UI.
4. Configure the approved GitHub client ID and encryption key through server-secret setup, then publish the saved Worker version privately. Either configure `GITHUB_CLIENT_SECRET` there too, or have the user enter the already approved existing client secret directly in the private `/setup` form after publication. Never export it through browser-tool output.
5. Open the Site and complete GitHub installation/authorization. Register only the one intended repository and verify the live status tool reports connected.
6. Use Sites' generated private plugin for MCP OAuth. Verify discovery, a catalogue read and unauthenticated denial through the actual client. Test a repository mutation only when the specific real entry and PR creation are authorized; never publish a synthetic fixture.

Until these steps complete, this is tested source, **not a deployed or connected OAuth service**.
