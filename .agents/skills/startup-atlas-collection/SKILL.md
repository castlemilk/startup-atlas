# Startup Atlas collection and MCP

Read repository `AGENTS.md` and `docs/AGENT-RUNBOOK.md`; inspect current main, open PRs, running work and deployment before making changes. Avoid overlapping another active update.

## Collect

1. Search the existing partner index and reviewed records. Verify the exact organisation and official website from primary evidence before adding it to `data/partner-logo-seeds.csv`; keep aliases and provider relationships separate. Add a CDN host only after confirming it on that official site.
2. Run `npm run crawl -- partners --follow 0`, then `npm run crawl -- logos --approved data/partner-logo-seeds.csv --partners-only --follow 0 --logo-limit 3`, and `npm run crawl -- partner-candidates --approved data/partner-logo-seeds.csv --snapshot research/crawl/latest-logos.json`. Use the manual Partner research crawl workflow when the local environment cannot resolve public hosts. Inspect source statuses and retrieve its review artifact.
3. For deeper firm research, run `npm run crawl -- profiles --approved data/partner-logo-seeds.csv --follow 2` (optionally `--partner` or `--limit`). Treat names, context, candidate links and captured dates as review leads; verify each role or company relationship against the source before adding a profile entry. Profile candidates are never automatically published.
4. For headshots, run `npm run crawl -- portraits --approved data/company-profile-seeds.csv --follow 2`. It runs the company-profiles crawl and then fetches portrait bytes for professional-bio headshot candidates (same-host or approved asset host only; LinkedIn and other social hosts are never fetched; scoped rows never authorize an asset download). Portrait files are opaque `.bin` research artefacts, exactly like logo captures.
5. Publish a reviewed logo or portrait only through the asset pipeline in `docs/MCP-ASSETS.md`: inspect the captured bytes, convert raster files with `scripts/atlas_assets.py convert`, stage with `validate` → `stage` → `prepare` (the review gate — unreviewed assets cannot prepare), then `scripts/publish_asset.py` (use `--dry-run` first). It writes the bytes to `web/assets/logos/` or `web/assets/portraits/`, the public-safe manifest to `web/assets/manifests/`, and the `web/logos.js` entry or the person's `photo`/`photo_url` field. Never hand-edit the map for a reviewed asset and never commit unreviewed captures — the repo is public and the 14-day crawl artifact is the only thing deleting them.
6. Do not request or inspect robots.txt, as directed by the owner. Preserve HTTPS and approved-host checks, public-address checks, rate limits, 429 stop handling, byte/time limits and opaque staging. Never bypass access challenges.
7. Distinguish discovered candidates, captured bytes, reviewed assets and published logos. Inspect image content, identity, provenance and usage terms; a page can contain portfolio logos or social graphics. Publish only a reviewed asset mapped explicitly to the exact directory name. Record source and review date; do not infer a provider affiliation from a name or logo.
8. Review metadata and geography against primary evidence. An office or programme location is not programme eligibility. Keep unknown and historical screenshot associations explicitly unverified.
9. Before starting a crawl, check the coordination registry first, then record the run. Query `atlas_list_crawl_runs` and `atlas_get_crawl_claims` for the sources you plan to crawl: a live claim means another worker owns that source until its lease expires, so do not start on it; a stale claim (expired lease, run still `running`) must be recovered explicitly, with the evidence recorded, before the source is re-claimed. Then record the run as described in `docs/CRAWL-COORDINATION.md` — run ID (`crawl-<YYYYMMDD>-<mode>-<nn>`), mode, sources, seed-file SHA-256, the 40-character main commit as `catalogue_revision`, `claimed_by`, `claimed_at`, a 30-minute lease for a partners run, and where the artifact will land — by appending to `data/crawl-runs.json` through the normal branch/review workflow until claim tools exist. After the crawl, update the same record with the outcome, snapshot SHA-256 and artifact URL, and keep `review_status: unreviewed` until a human has read the candidates. The coordination registry is advisory only — a claim does not authorise fetching a source and never overrides a transport guard.

## MCP and publication

1. Check `atlas_get_connection` and live tool discovery; search before writing. Confirm the deployed MCP's capabilities rather than assuming a repository implementation is live.
2. For new opportunities, verify current programme terms and source URLs; call `atlas_validate_opportunity`, then pass its revision to `atlas_add_opportunity` only when the user requested that source-backed entry. Reference the crawl `run_id` in the proposal so the published entry traces back to the crawl that found it. Inspect the resulting draft PR, generated data and CI before merging. Duplicate validation should not persist data.
3. For partner updates, use `atlas_validate_partner` and `atlas_propose_partner` only when exposed by the live MCP. Reference the crawl `run_id` in the proposal, as above. If unavailable, report the deployment gap; do not represent a GitHub-only edit as an MCP write. Never replay an uncertain write or OAuth exchange; inspect resulting PRs first.
4. Run appropriate tests, merge only within the user's authorization, and verify Pages and private MCP deployments independently. After publication, verify an exact search and a typo search against fresh data. Browser search builds its Fuse index from the published catalogue; drafts are not searchable.
5. Report counts separately for discovered, captured, reviewed and published records, with sources, failure statuses and limitations. Do not claim unreviewed candidates are new firms or deployed logos.

For OAuth, Workers fetch/redirect constraints, workflow commands and deployment troubleshooting, consult `docs/AGENT-RUNBOOK.md`.

## Company profiles, portraits and social references

Use `python3 scripts/crawl.py company-profiles --approved data/company-profile-seeds.csv --partner PsiQuantum --follow 2` for the reviewed company seed example. The CSV uses the existing `partner` column for compatibility, but this mode validates names against `data/startup-research.json` and requires the reviewed official website host. Do not add company names to the partner importer to bypass identity checks. Team/portfolio/About discovery is bounded by `--follow`; all transport limits and the no-robots rule above remain in force.

Company packets preserve page descriptions, structured subject claims, logo candidates, labelled images and accessible-label social links. They do not fetch image/social destinations or establish headshot identity, employment, account verification or asset-use permission. Preserve source URL and observation date; counts are page-scoped observations and can repeat the same asset/account. Report successful empty pages separately from failed fetches.

Before publication, verify the exact subject and cited primary source, preserve attribution, and review rights separately from availability. A press download is not automatically a licence. When permission is unresolved, retain the candidate and cite the official source without copying or embedding the image. Outbound links found on an official homepage may be described as homepage-linked references, not independently verified accounts. Confirm the generated graph and live profile after a reviewed update; record Pages and MCP graph revisions without claiming a separately hosted MCP code deployment.
